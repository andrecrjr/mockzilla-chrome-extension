Overview

Architecture & Tech Stack

Mockzilla HTTP Server is a powerful Next.js application with PostgreSQL database, built with modern web technologies. It provides a comprehensive API mocking platform with dynamic response generation, stateful workflows, and AI integration via Model Context Protocol (MCP).

Tech Stack

  • Framework: Next.js 16 with App Router
  • Runtime: Bun
  • Language: TypeScript
  • Database: PostgreSQL with Drizzle ORM
  • Styling: Tailwind CSS 4
  • UI Components: Radix UI
  • Forms: React Hook Form + Zod
  • Deployment: Docker

Core Features

  • Dynamic Response Generation with JSON Schema + Faker
  • Stateful Workflows with persistent state & logic
  • Mini-Database for transient data
  • First-class MCP (Model Context Protocol) Support
  • Folder Organization for mock grouping
  • Export/Import for backup & sharing

Installation

Quick Start

Using Docker (Recommended)

// Copy environment template
cp .env.example .env
// Start development environment
make dev-up
// Visit application at: http://localhost:36666

Using Bun (Local Development)

// Install dependencies
bun install
// Set up environment variables
cp .env.example .env
// Update DATABASE_URL to: postgresql://mockzilla:mockzilla@localhost:5432/mockzilla
// Run database migrations
bun run db:push
// Start development server
bun run dev

Core Endpoints

GET /api/folders

  • id - Get specific mock (optional)

  • limit - Items per page (optional, default: 10)

Create a new mock

Request Body:
{

  "bodyType": "json|text" (optional, default: "json"),

}

Access a specific mock endpoint

Workflow Scenarios

Stateful Workflows

Mockzilla provides powerful workflow scenarios that allow you to create complex, stateful API interactions. Each scenario can have multiple transitions with conditions, effects, and responses.

Conditions

Conditions determine when a transition should execute. They are evaluated against the input context.

Supported Condition Types:
  • eq - Equals
  • neq - Not Equals
  • exists - Field exists (not null/undefined)
  • gt - Greater Than
  • lt - Less Than
  • contains - Array includes or string substring

Effects

Effects are actions that modify the state or database during a transition.

Supported Effect Types:
  • state.set - Set state variables
  • db.push - Add row to table
  • db.update - Update rows
  • db.remove - Remove rows

First Workflow: Login & Dashboard Flow

1

Create a Scenario

Think of a scenario as a container for one specific feature.

Name: auth-flow
2

Define Login Transition

When user hits POST /login, set a flag.

Effects (What happens): 
                                        [
                                          { "type": "state.set", "raw": { "isLoggedIn": true }},
                                          { "type": "state.set", "raw": { "user": "{{input.body.username}}" }}
                                        ]
3

Protect the Dashboard

Create GET /dashboard that only works if logged in.

Conditions (The Guard): 
                                        [
                                          { "type": "eq", "field": "state.isLoggedIn", "value": true }
                                        ]

If this condition fails, it returns 404 (or the next matching transition).

4

Test It!

Use the Test Workflow tab or curl.

1. POST /login (Success!)
2. GET /dashboard (Access Granted!)

Workflow Example

// Example workflow scenario with transitions for shopping cart
{
  "scenarios": [
    {
      "id": "shopping-cart",
      "name": "Shopping Cart Workflow",
      "description": "Handles cart operations"
    }
  ],
  "transitions": [
    {
      "scenarioId": "shopping-cart",
      "name": "Add Item to Cart",
      "path": "/cart/add",
      "method": "POST",
      "conditions": [
        {
          "type": "eq",
          "field": "input.body.type",
          "value": "item"
        }
      ],
      "effects": [
        {
          "type": "db.push",
          "table": "cart",
          "value": "{{input.body}}"
        }
      ],
      "response": {
        "status": 201,
        "body": { "message": "Item added to cart", "id": "{{input.body.id}}" }
      }
    }
  ]
}

In this example, the workflow defines a scenario ("shopping-cart") with transitions that handle cart operations. When a POST request is made to /cart/add with a body containing {type: "item"}, the system adds the item to the cart database and returns a 201 status with a success message.

MCP Integration

Model Context Protocol (MCP)

Mockzilla exposes a Model Context Protocol server, allowing AI agents to fully control mocking capabilities. This enables AI-assisted development where AI agents can create and manage mocks programmatically.

MCP Server Setup

Add this configuration to your AI agent's MCP settings (e.g., in mcp.json or IDE settings):

{   "mockzilla": {     "command": "npx",     "args": [       "-y",       "mcp-remote",       "http://localhost:36666/api/mcp"     ]   } }

Available MCP Tools

  • create_mock - Create new mock endpoints with specified responses
  • create_workflow_transition - Define workflow rules with conditions and effects
  • inspect_workflow_state - Read scenario state and database contents
  • reset_workflow_state - Clear scenario data for a fresh start
  • update_mock - Update existing mock configurations
  • delete_mock - Remove mock endpoints
  • create_schema_mock - Create mocks with dynamic JSON schema generation

Quick Start

Once configured, your AI agent can interact with Mockzilla using natural language commands like "Create a mock for GET /users" or "Set up a login workflow".

Chrome Extension Sync

Server-Extension Synchronization

Mockzilla provides seamless synchronization between the Mockzilla Chrome Extension and the server, allowing you to share mocks across your team and environments.

How It Works

1.
Enable Sync in Extension: Navigate to the extension options page and enable "Mockzilla Server Sync" for any group you want to sync.
2.
Configure Server URL: Set your Mockzilla server URL (default: http://localhost:36666).
3.
Sync Your Mocks: Click "Sync Now" to push your extension mocks to the server. They will appear as folders with "-extension" suffix.
4.
Share with Team: Team members can use the same Mockzilla server to access synced mocks and maintain consistency.

Sync API Endpoint

POST /api/sync/extension

The sync endpoint accepts a JSON payload with your extension groups and mocks. It automatically creates or updates folders and mocks on the server.

Request Format

{
  "groups": [
    {
      "id": "string",
      "name": "string",
      "description": "string",
      "mocks": [
        {
          "id": "string",
          "name": "string",
          "pattern": "string",
          "response": "string",
          "statusCode": "number",
          "matchType": "exact|substring",
          "enabled": "boolean"
        }
      ]
    }
  ]
}

Auto Sync

When auto-sync is enabled in the extension, changes are automatically synchronized to the server, ensuring your team always has the latest mock definitions.
